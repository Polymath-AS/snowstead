# Helios V1 Architecture

## Goal

Helios v1 is a Cloudflare-native binary cache that serves standard Nix read
endpoints from Cloudflare Workers while storing blobs in `R2` and cache
metadata in `D1`.

The first version optimizes for a small, reliable implementation that fits
Cloudflare's execution model. It does not try to be a drop-in rewrite of
`atticd`.

## Decisions

### Protocol Scope

Helios v1 supports two surfaces:

- Standard Nix binary cache reads for consumers.
- A Helios-native authenticated write API for publishers.

Attic-compatible write flows are explicitly out of scope for v1. Attic's
single-request upload model assumes a server process that can receive and
transform a full upload inline. Helios v1 instead uses upload sessions so
large artifacts can reach `R2` without depending on one Worker request.

### Access Model

Reads are public in v1.

Writes require authentication. The exact token format is an implementation
detail, but the Worker is the authority for creating upload sessions and
publishing metadata.

### Storage Model

- `R2` stores final binary artifacts.
- `D1` stores cache configuration, published path metadata, upload
  sessions, and garbage-collection state.
- `Durable Objects` are not part of the initial design.

`D1` is sufficient for the first version if publish and finalize flows are
modeled as idempotent state transitions with uniqueness constraints.
If we later discover that publish contention needs a single-writer
coordinator, we can add a narrow `Durable Object` around finalize without
rewriting the read path.

### Dedup And Compression

Helios v1 does not implement Attic-style server-side chunking or global
deduplication.

Each published store path maps to one compressed NAR object in `R2`.
Dedup is limited to content-addressed object reuse when two publish flows
produce the same final blob key.

This is a deliberate tradeoff:

- It avoids server-side streaming transforms inside the Worker.
- It keeps upload and finalize semantics simple.
- It fits direct-to-`R2` upload flows.

## Data Model

### R2 Object Keys

Final blob keys are content-addressed by compressed file hash:

`nars/sha256/<file-hash>/<compression>.nar`

Examples:

- `nars/sha256/0v9z.../zstd.nar`
- `nars/sha256/1k2m.../none.nar`

Rationale:

- The key is stable for identical final artifacts.
- The key is derived from the served file, not transient upload state.
- Compression is explicit in the path and narinfo metadata.

Helios v1 does not store narinfo as an object in `R2`. Narinfo responses are
materialized from `D1` metadata and signed by the Worker.

### D1 Records

The initial schema should include these logical tables:

- `caches`: cache identity and read policy.
- `published_paths`: one row per published store path within a cache.
- `blob_objects`: final `R2` object key, file hash, file size, compression,
  and object integrity metadata.
- `upload_sessions`: in-progress or aborted publish attempts.
- `upload_parts`: client-reported multipart state when needed.
- `gc_marks`: retention and cleanup bookkeeping.

`published_paths` should be keyed by cache plus store path hash. That makes
read lookups direct and makes publish retries naturally idempotent.

## Endpoint Shape

### Public Read Endpoints

These endpoints follow standard Nix binary cache behavior:

- `GET /:cache/nix-cache-info`
- `GET /:cache/:storePathHash.narinfo`
- `HEAD /:cache/:storePathHash.narinfo`
- `GET /:cache/nar/:storePathHash.nar`

The read path works like this:

1. Resolve the cache and published path in `D1`.
2. Build narinfo from metadata.
3. Sign narinfo before returning it.
4. For NAR downloads, either stream from the Worker via `R2` or redirect to
   a short-lived signed `R2` URL.

Redirected downloads are preferred in production because they keep the
Worker off the hot data path for large blobs.

### Helios Write Endpoints

These endpoints are Worker-owned and intentionally not Attic-compatible:

- `POST /_api/v1/caches/:cache/upload-sessions`
- `POST /_api/v1/uploads/:sessionId/multipart`
- `POST /_api/v1/uploads/:sessionId/complete`
- `POST /_api/v1/uploads/:sessionId/publish`
- `POST /_api/v1/get-missing-paths`

Their responsibilities are:

- Create an authenticated upload session with expected metadata.
- Return direct upload instructions for single-part or multipart `R2`
  uploads.
- Validate that the upload completed.
- Publish the path atomically into read-visible metadata.
- Tell publishers which paths are already present.

## Upload Flow

### Small Uploads

For small objects, the Worker may mint a direct single-part upload target to
`R2` and record the expected file hash and file size in `upload_sessions`.

### Large Uploads

For large objects, the Worker creates an `R2` multipart upload and returns a
session payload that lets the publisher upload parts directly to `R2`.

The client owns the actual blob transfer. The Worker owns:

- authorizing the session
- recording expected metadata
- validating completion
- publishing the path after the blob is durable

This split is the core Cloudflare-native design decision in v1.

### Client Responsibilities

The publishing client is responsible for:

- producing the NAR
- applying the chosen compression
- computing file hash and file size
- providing narinfo fields such as references, deriver, nar hash, nar size,
  and system when available

Helios v1 does not compress or rechunk uploads inside the Worker.

## Publish Semantics

Publishing a path is a metadata transaction, not a blob upload.

A path becomes visible to readers only after these conditions hold:

1. The blob exists in `R2`.
2. The blob metadata matches the session's expected hash, size, and
   compression.
3. The `published_paths` row is committed in `D1`.

Retries must be safe. If the same publish request is replayed after a
successful commit, Helios should return the already-published result instead
of creating duplicate state.

## Signing

Narinfo responses are signed by the Worker using a cache signing key stored
as a secret.

V1 stores the canonical narinfo fields in `D1` and signs the response from
those fields. We may later cache rendered narinfo text or signatures if read
volume makes that worthwhile.

## Garbage Collection

Garbage collection runs from a Cron-triggered Worker entrypoint.

V1 garbage collection covers two cases:

- expiring abandoned upload sessions
- deleting unreferenced blob objects after metadata says they are safe to
  remove

Incomplete multipart uploads should also be protected by `R2` lifecycle
rules so abandoned uploads do not accumulate forever.

## Non-Goals

These are intentionally excluded from v1:

- Attic protocol parity for uploads
- server-side chunking and global deduplication
- private-read caches
- multi-region coordination beyond what Cloudflare provides by default
- full admin APIs for cache management

## Implementation Order

1. Shared domain types and input parsing.
2. Worker bindings for `R2` and `D1`.
3. `D1` schema and repository layer.
4. Public Nix-compatible read endpoints.
5. Helios-native upload sessions and publish flow.
6. Narinfo signing.
7. Cron-based garbage collection.

## Unresolved Questions

- Should downloads redirect to signed `R2` URLs by default, or only above a
  size threshold?
- Do we want one cache-level signing key or one key per cache?
- Should the first publisher client be a standalone CLI or a library used by
  existing build tooling?
